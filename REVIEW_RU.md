# Проверка и исправления — версия 1.2

Проверены GET-сканер `scanner.py`, POST-сканер `post_scanner.py`, общий пакет `bbscanner` и оркестратор `pipeline_manager.py`. Внешние сайты не сканировались. Автоматические проверки используют localhost, фиктивные ответы и тестовые дочерние процессы.

## Исправленные ошибки

| Проблема | Исправление |
|---|---|
| CRLF-мутация POST перекодировывала соседние поля: например, `%2526` могло превратиться в `%26` | Заменяется только выбранное вхождение; остальные части формы сохраняются побайтно |
| SSTI/CRLF-находки со статусом `confirmed_signal` не учитывались в POST-счётчике подтверждений | Сводка считает подтверждённые сигналы всех модулей |
| Некоторые таймауты POST выглядели как отсутствие находок | Ошибки сохраняются отдельно; проверки получают `inconclusive`, итог различает частичный и завершённый проход |
| Ошибки SSRF-проб могли не отражаться в общем статусе | OAST остаётся ожидающим ручной проверки, а таймаут отмечается как ошибка и `delivery_unknown` |
| Отмена asyncio-задач могла оставить workers активными при закрытии HTTP-клиента | Общий ограниченный пул отменяет задачи и дожидается их завершения |
| Проверка исчерпанного POST-бюджета ждала следующего слота rate limit | Бюджет проверяется до ожидания; неотправленная OAST-проба не попадает в журнал |
| Неоднозначный JSON молча терял повторяющиеся ключи; NaN/Infinity проходили разбор | Строгий JSON-разбор отклоняет эти случаи, непредставимые числа и некорректный Unicode |
| IPv6-адрес POST терял квадратные скобки; заголовки с разным регистром дублировались | Общая нормализация URL и регистронезависимые пользовательские заголовки |
| Пользовательские POST-заголовки могли уходить на все origin входного списка | Добавлена явная привязка через `--headers-origin`; для одного origin она автоматическая |
| `--output '~/...'` проверялся по раскрытому пути, но дальше использовался исходный | Во всех стадиях используется раскрытый абсолютный путь |
| Один `[extensions]` мог считаться подтверждённым чтением файла | Слабая сигнатура остаётся кандидатом; подтверждение требует структуры файла, контроля и повтора |
| Усечение тела мешало CRLF-проверке уже полученных заголовков | Проверка заголовков отделена от проверки полноты тела |
| Исключение внутри GET-ветки serial могло не дать запуститься POST | Исключения веток изолированы и записываются в лог |
| Неизвестный/нестроковый статус в summary сканера обрабатывался некорректно | Оркестратор проверяет формат и допустимые значения; продолжает следующие стадии |
| `--dry-run` зависел от бюджета реальных сканеров | Подготовка файлов выполняется до проверки лимитов запуска сканеров |

## Улучшения отчётов и ввода

- Находки POST записываются в `findings.jsonl` и TXT сразу по мере обнаружения. При Ctrl+C/SIGTERM сохраняется частичная сводка; код выхода — 130.
- GET и POST используют единый формат строки с состоянием, модулем, URL, параметром и payload. Русский текст читается нормально; переносы строк, ANSI и управляющие Unicode-символы из ответов экранируются.
- POST принимает JSON Pointer в `--params`, например `/items/0/name`; путь поля входит в машинный отчёт.
- Добавлен `--max-targets` для POST. Лимит конкурентности и лимит запросов в секунду остаются разными настройками.
- Логи subprocess сохраняются по мере чтения; рабочие отчёты не включены в архив исходников.

## Что проверено

**77 тестов прошли** в Python 3.12. Все 24 Python-файла также разобраны с грамматикой Python 3.10; отдельный запуск на интерпретаторе 3.10 не выполнялся.

Проверки охватывают:

- положительные и отрицательные сигналы семи модулей, baseline и контроль;
- GET query, POST-формы, JSON, дубликаты параметров и сохранение соседних значений;
- HTTP 500 с SQL-ошибкой, потоковое тело, неизвестную кодировку, неполное тело и таймауты;
- OAST-журнал, отмену CLI и сохранение отчётов без настоящего OAST-сервиса;
- rate, конкурентность, бюджет запросов и отсутствие переходов на внешний redirect;
- передачу аргументов реальным GET/POST CLI из оркестратора;
- serial/parallel, падение процесса, исключение ветки, зависшего потомка и некорректный summary.

Для повторения после установки зависимостей:

```bash
python -m unittest discover -v
```

## Обновление

Распакуй `bug_bounty_scanner_v1.2.zip` в отдельную папку, затем:

```bash
cd bug_bounty_scanner
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
python -m unittest discover -v
```

Копировать только один `.py` недостаточно: всем трём CLI нужен соседний пакет `bbscanner`. Рабочие targets, POST-шаблоны и авторизационные данные переноси из своей конфигурации; для нового прохода используй новую/пустую папку результатов.

Основные команды прежние. Новое требование: если у POST несколько origin и передаются пользовательские заголовки или cookies, укажи `--headers-origin 'https://нужный-хост'`. Выбор `ssrf` требует собственного `--oast-domain`.

## Пределы проверки

Совпадение сигнатуры не доказывает эксплуатацию во всех контекстах: XSS и SQLi сохраняются как кандидаты. SSTI/CRLF/LFI/Redirect могут подтвердить технический признак; его влияние оценивается вручную. SSRF автоматически не подтверждается — UUID нужно сопоставить с DNS/HTTP-логами своего сервера. Реальные WAF, авторизация/обновление CSRF, произвольные бизнес-процессы и совместимость с любой версией внешнего Recon этим стендом не проверяются.
