# Bug Bounty Scanner 1.3 — Python

Модульный асинхронный сканер базовых признаков **Reflected XSS, LFI/Path Traversal, Open Redirect, error-based SQLi, SSRF/OAST, SSTI и CRLF**. Принимает URL или файл URL, использует `aiohttp`, `BeautifulSoup` и `colorama`. Проверки выполняются GET-запросами по целям, разрешённым программой.

В версии 1.3 четыре новых модуля используют `run(send, baseline, **kwargs) -> Outcome`; интерфейс, типы результатов и подключение описаны в [MODULES_API_RU.md](MODULES_API_RU.md).

## Установка и первый запуск

Нужен Python 3.10 или новее. Распакуй архив целиком: `scanner.py` использует соседний пакет `bbscanner`.

```bash
cd bug_bounty_scanner
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

python scanner.py -u 'https://example.com/search?q=test' \
  --workers 10 --rate 5 --timeout 5 --output scan_results
```

Здесь и далее `example.com` — пример. Если создание venv на Ubuntu не работает, установи `python3-venv` через пакетный менеджер.

URL с `&` всегда заключай в кавычки. По умолчанию работают `xss,lfi,redirect`; дополнительные модули включаются через `--modules`. Результат: `scan_results/vulns_report.txt`. Повторный запуск должен использовать новую или пустую папку; старые отчёты не перезаписываются.

## Список URL

Создай `urls.txt`, по одному адресу на строку:

```text
https://example.com/search?q=test
https://example.com/download?file=manual.txt
https://example.com/login?next=/account
```

```bash
python scanner.py -l urls.txt --workers 10 --rate 5 \
  --max-requests 1000 --output results_batch
```

Разрешены пустые строки и комментарии, начинающиеся с `#`. URL дедуплицируются. Можно также несколько раз указать `-u`. Файл `parameterized_urls.txt` из ранее подготовленного crawler подходит по формату, но для GET-проверок отбирай подходящие endpoints с учётом их метода и scope.

## Как находятся параметры

1. Если URL уже содержит query, проверяются её параметры. Повторяющиеся имена рассматриваются по отдельным вхождениям.
2. Если query нет, сканер загружает страницу и находит ссылки с query и GET-формы **того же origin** — scheme + hostname + port.
3. Это один уровень извлечения из исходной страницы; рекурсивного обхода здесь нет. POST-формы пропускаются.
4. Параметры можно задать явно:

```bash
python scanner.py -u 'https://example.com/search' \
  --params q --modules xss --no-discovery --output results_xss
```

`--params` одновременно ограничивает проверяемые имена и добавляет отсутствующие имена с пустыми значениями. Это гипотезы пользователя; сканер не доказывает, что сервер их поддерживает. Без найденных/заданных параметров статус будет `no_testable_parameters`, а не «сайт безопасен».

Исходные URL определяют разрешённые origin. Сканер не расширяет их до всех поддоменов. Для программы с ограничением по конкретным путям используй явный список URL и `--no-discovery`. На стартовые редиректы сканер тоже не переходит: передай конечный разрешённый URL самостоятельно.

## Что делает каждый модуль

| Файл | Проверка |
|---|---|
| `bbscanner/checks/xss.py` | Неисполняемые уникальные маркеры и точное отражение в HTML |
| `bbscanner/checks/lfi.py` | Два пути к файлам, сигнатуры, отрицательный контроль и повтор |
| `bbscanner/checks/redirect.py` | Статус 3xx и управление внешним hostname в Location |
| `bbscanner/checks/sqli.py` | SQL-ошибки MySQL/PostgreSQL/MSSQL/Oracle, baseline и контроль |
| `bbscanner/checks/ssrf.py` | Уникальный OAST URL и журнал UUID; подтверждение только по вашему логгеру |
| `bbscanner/checks/ssti.py` | Арифметика шаблонизаторов с baseline и повтором |
| `bbscanner/checks/crlf.py` | Маркер `X-CRLF-Scan` в заголовках ответа |

### Новые модули

Выбор модулей задаётся через `--modules`:

```bash
python scanner.py -u 'https://target.example/search?q=test' \
  --modules sqli,ssti,crlf --output new_checks
```

SQLi отправляет только error-based пробы (`'`, `"`, `)`, `';`, `";`, `/*`) и ищет узнаваемые сообщения MySQL, PostgreSQL, MSSQL и Oracle. Ответ HTTP 500 с полным телом анализируется, но сам по себе не доказывает SQLi.

SSRF включается только вместе с собственным доменом взаимодействий:

```bash
python scanner.py -u 'https://target.example/fetch?url=https://example.org' \
  --modules ssrf --oast-domain 'your-issued-oast.example' --output ssrf_results
```

Для каждого параметра создаётся `http://<uuid>.your-issued-oast.example/probe`. Файл `oast_probes.jsonl` и терминал показывают UUID и факт попытки отправки. Найти SSRF можно только после проверки DNS/HTTP-логов своего OAST-сервера; HTTP-ответ цели не считается подтверждением.

SSTI проверяет `{{7*7}}`, `${7*7}`, `<%= 7*7 %>` и `<%=- 7*7 %>` (последнее корректно даёт `-49`). Число сравнивается с baseline и контролем. CRLF проверяет наличие заголовка `X-CRLF-Scan` в ответе, а не строку в теле. Все эти результаты являются автоматическими признаками и требуют ручной проверки контекста.

### Reflected XSS

В одно вхождение параметра подставляется `idxss_<случайный_nonce>">`. Остальные query-компоненты сохраняются. Проверяется точное наличие маркера в исходном HTML; HTML-entities перед проверкой не декодируются. Поэтому `&quot;&gt;` не принимается за отражение исходного `">`.

Если маркер найден, отправляется второй запрос с новым nonce. Результат всегда имеет статус **`candidate`**, даже если отражение повторилось: нахождение кавычки и угловой скобки не доказывает выполнение JavaScript. Важны HTML/JS-контекст, CSP и другие условия. JSON/text-ответы не считаются HTML XSS. Исполняемые `<script>`/event-handler payload не отправляются, браузер не запускается.

### LFI / чтение файлов

Используются только два базовых payload:

```text
../../../../etc/passwd
../../../../windows/win.ini
```

Поиск сигнатур: `root:x:0:0:` и `[extensions]`. Обычный ответ до подстановки — **baseline**. Если сигнатура уже есть в baseline, она не принимается за доказательство новой инъекции.

После совпадения выполняются отрицательный контроль с заведомо вымышленным путём и повтор исходной пробы. Если сигнатура есть также в ответе на вымышленный путь, результат не подтверждается. Ожидаемый 404 у отсутствующего контрольного файла учитывается отдельно от ошибок сканирования.

Для `confirmed_signal` нужны воспроизводимость, чистый контроль и структура passwd-строки либо дополнительная типичная INI-секция. Один `[extensions]` остаётся кандидатом. Если подтверждение не удалось из-за сети или бюджета, первоначальное совпадение сохраняется как кандидат.

Такой ответ показывает признаки чтения файла, но не устанавливает серверный механизм: это может быть Path Traversal, LFI или другая ошибка обработки файла. Отсутствие этих сигнатур не исключает другие варианты уязвимости. Более глубокие обходы, wrappers и техники обхода фильтров не реализованы.

### Open Redirect

По умолчанию проверяются имена вроде `next`, `redirect`, `return_url`, `continue`, `dest`, `url`, `callback`. Для всех имён можно добавить `--redirect-all-params`.

В качестве внешней цели используется уникальный `https://bb-<nonce>.example.invalid/probe/<nonce>`. Проверяется статус из `301,302,303,307,308` и **hostname разобранного Location**, а не наличие строки payload где-либо в заголовке.

Второй запрос использует другой внешний hostname. Если Location следует за обеими подстановками, сохраняется `confirmed_signal`. Статический редирект на один внешний адрес и ссылка вида `https://свой-сайт/?next=https://чужой-сайт/` не проходят эту проверку. Переход по Location не выполняется, внешний сервер не запрашивается. Meta-refresh и JavaScript-редиректы не проверяются.

## Авторизация через cookies

Один origin:

```bash
python scanner.py -u 'https://example.com/account?tab=profile' \
  --cookies 'session=YOUR_SESSION; preference=en' --output results_auth
```

Чтобы значение Cookie не попадало прямо в командную строку, сохрани его в локальный файл с ограниченными правами:

```bash
chmod 600 cookies.txt
python scanner.py -l urls.txt --cookies-file cookies.txt \
  --cookie-origin 'https://example.com' --output results_auth_batch
```

В файле должна быть строка `session=...; preference=...`, без префикса `Cookie:`. Для списка с несколькими origin обязателен `--cookie-origin`: cookies отправляются только выбранному origin из этого списка. Например, cookies для HTTPS не отправятся на HTTP или другой поддомен.

Значение Cookie не включается в журнал HTTP-запросов или настройки отчёта. Автоматический cookie jar и наследование `.netrc`/proxy-переменных отключены. Ответы Set-Cookie не обновляют переданное значение. Получение/обновление сессии, CSRF и проверка успешности входа не автоматизированы. Просроченная сессия может привести к проверке страницы входа вместо нужного раздела.

## Параллельность и ограничения

| Опция | По умолчанию | Значение |
|---|---:|---|
| `--workers` | 10 | Параллельные задачи/HTTP-запросы |
| `--rate` | 5 | Общий лимит начала запросов в секунду |
| `--timeout` | 5 | Сетевой таймаут одного запроса, включая чтение тела |
| `--max-requests` | 1000 | Общий бюджет baseline, проб, контролей и подтверждений |
| `--max-targets` | 100 | Максимум исходных и обнаруженных URL |
| `--max-parameters` | 20 | Максимум query-вхождений на URL |
| `--max-bytes` | 1048576 | Максимальный анализируемый объём ответа, 1 MiB |
| `--modules` | xss,lfi,redirect | `xss,lfi,redirect,sqli,ssrf,ssti,crlf` через запятую |
| `--oast-domain` | — | Обязателен при выборе `ssrf`; только DNS-имя вашего логгера |
| `--user-agent` | Случайный на URL | Фиксированный User-Agent при необходимости |
| `--no-discovery` | Выключено | Проверять только явно переданные URL/параметры |

Случайный User-Agent выбирается для URL и остаётся одинаковым в baseline, пробах и контролях этого URL. Так смена UA не мешает сравнению ответов. Смена UA не гарантирует прохождения WAF; если программа требует идентификацию, задай нужный `--user-agent`.

`--rate` относится ко всему сканеру, а не к каждому worker. Используй значение, разрешённое программой. Один query-параметр обычно порождает несколько запросов: основная проба, при необходимости контроль и подтверждение. DNS/TCP-пакеты не являются единицей этого HTTP-бюджета.

Реализованы обработка timeout, TLS/connection errors и HTTP 4xx/5xx. Такие ответы сохраняются как ошибки/неопределённые проверки; остальные цели продолжают обрабатываться. Проверка TLS включена. Внутренний повтор GET после разрыва соединения подавлен публичным middleware aiohttp, чтобы он не обходил счётчик и rate limit. При исчерпании бюджета скан прекращает новые запросы и сохраняет результаты.

Большие ответы обрезаются и помечаются как неполные. SQLi/SSTI требуют полного тела, CRLF проверяет уже полученные заголовки независимо от усечения тела. Ctrl+C/SIGTERM сохраняют уже завершённые проверки; незавершённая проверка может не успеть дать находку. Параллельные задачи отменяются и дожидаются завершения перед закрытием HTTP-сессии.

Сетевая ошибка SSRF-пробы сохраняется одновременно как ошибка запроса и как ожидающая проверки OAST-проба: таймаут не означает, что сервер не успел обратиться к логгеру. Для неё записывается `delivery_unknown`; проверь UUID в своих DNS/HTTP-логах.

## Отчёты и интерпретация

В терминале ярко-красным показываются подтверждённые признаки, жёлтым — кандидаты. В перенаправленном выводе ANSI-коды не используются.

| Файл | Содержимое |
|---|---|
| `vulns_report.txt` | Все находки, включая кандидатов, с явным уровнем подтверждения |
| `findings.json` | Находки в машинном формате |
| `checks.jsonl` | Итог проверки; у новых модулей confirmed/negative/skipped/inconclusive/oast_pending, у прежних также candidate/confirmed_signal |
| `requests.jsonl` | URL, назначение запроса, статус, время, ошибки и SHA-256 прочитанного тела |
| `oast_probes.jsonl` | UUID SSRF-проб, payload и состояние отправки/ответа; не подтверждение взаимодействия |
| `errors.json` | Неожиданные HTTP/сетевые ошибки; ожидаемый контрольный 404 исключён |
| `targets.json` | Проверяемые endpoints и источник их обнаружения |
| `summary.json` | Итоги, ограничения и настройки без значения Cookie |

В находке есть URL с payload, параметр и индекс его вхождения, HTTP-статус, короткое доказательство и URL подтверждения. Полные ответы и полное содержимое системных файлов в отчёт не копируются. SHA-256 относится к прочитанному телу, которое может быть усечено.

**`confirmed_signal` — подтверждённый автоматическими проверками технический признак, а не гарантия принятия отчёта программой.** Реальный контекст и impact оцениваются вручную. `candidate` и `inconclusive` нельзя объявлять подтверждённой уязвимостью. `negative` означает, что конкретная реализованная проба не дала совпадения.

`Outcome.state="confirmed"` у новых модулей означает, что детектор воспроизвёл свой сигнал с контролем. Оценка находки хранится отдельно в `Signal.confidence`: например, SQL-ошибка остаётся `candidate`, даже если повторилась.

Отчёт может содержать чувствительные query-значения и фрагменты авторизованных страниц. На Linux новые файлы обычного CLI-запуска имеют права 600; не публикуй рабочие отчёты и cookies вместе с исходниками.

Коды выхода: `0` — проход завершён (возможны отдельные ошибки, см. summary); `1` — нет тестируемых параметров, бюджет исчерпан, все проверки неопределённы или общий сбой; `2` — аргументы/файлы; `130` — прерывание. Статус `completed_with_errors` означает, что часть запросов/проверок не удалась.

## Локальные тесты

```bash
python -m unittest discover -v
```

Проверены GET, POST-формы и JSON: SQLi с HTTP 500, SSTI с baseline, CRLF-заголовки, сохранение соседних полей, валидация OAST, таймауты, бюджет, конкурентность, остановка CLI и прежние XSS/LFI/Redirect-сценарии. Оркестратор проверяется на фиктивных дочерних процессах. Внешние сайты и реальные OAST-сервисы не используются.

Тесты используют localhost и вымышленные passwd/INI-ответы; реальные системные файлы, настоящие cookies и сторонние цели не используются. Проверенная среда: Python 3.12, aiohttp 3.13.5, BeautifulSoup 4.15.0, colorama 0.4.6.
